# 사업 PM용 Webhook 도입 플레이북

"웹훅으로 뭔가 하고 싶다"에서 실제 발송까지, PM이 무엇을 순서대로 정하고 무엇을 개발에 요청하는지.

원칙: **PM은 "무엇을/누구에게/무슨 값으로" 를 정하고, 개발은 "어떻게"를 만든다.** PM이 기술 스펙을 정할 필요는 없지만, 아래 4가지를 정해주지 않으면 개발이 착수할 수 없다.

---

## PHASE 1. 정의 — 개발 요청 전에 PM이 확정 (1~2일)

### STEP 1. 목적 한 문장으로 쓰기

> "**[누구]**에게 **[언제]** **[무엇]**을 보내서 **[어떤 행동]**을 유도한다"

예: "설치 후 24시간 접속하지 않은 유저에게 복귀 보상 메일을 보내 재접속을 유도한다"

이 문장이 안 써지면 나머지가 전부 흔들린다. 여기서 멈추고 목적부터 정리할 것.

### STEP 2. 채널이 정말 Webhook인지 확인 (중요)

| 하고 싶은 일 | 맞는 채널 | 개발 필요 |
|---|---|---|
| 폰 알림창에 푸시 알림 | **FCM** | 서버 개발 없음 |
| 앱 실행 중 팝업·배너 | **클라이언트** | 서버 개발 없음 (클라 렌더링만) |
| 인게임 우편함 보상 지급, 외부 시스템 연동 | **Webhook** | **서버 개발 필요** |

Webhook은 셋 중 개발 비용이 가장 크다. **FCM/클라이언트로 되는 일이면 그쪽이 정답.**
→ 결정: 우리는 ( ) 채널로 간다. 이유: ______

### STEP 3. 전달물 스키마 정의 ★ PM의 핵심 산출물

메시지에 어떤 값이 들어가는지 표로 정한다. **이 표가 그대로 개발 명세가 된다.**

| 필드명 (영문) | 무엇인가 | 필수 | 예시값 |
|---|---|---|---|
| `title` | 메일 제목 | ✓ | 복귀 보상이 도착했어요 |
| `body` | 메일 본문 | ✓ | 7일 출석 보상을 확인하세요 |
| `reward_id` | 지급할 보상 코드 | — | comeback_pack_01 |
| `expire_days` | 메일 만료일 | — | 7 |

작성 요령:
- 운영자가 태스크마다 **바꿔서 입력할 값**만 필드로 만든다. 항상 고정인 값은 필드로 만들지 않는다.
- 보상 코드는 **기존 기획 데이터의 코드 체계를 그대로** 쓴다 (새로 만들지 말 것)
- 필드명은 나중에 바꾸기 어렵다. 확장 가능성을 미리 생각할 것 (예: 딥링크 추가 여지)

### STEP 4. 대상·운영 정책 정하기

- **대상 조건**: 예) 설치 후 24h 미접속, 최근 3일 미접속, 특정 국가 등
- **발송 시점**: 1회성 / 정기 / 트리거(행동 발생 즉시)
- **발송 빈도 상한**: 유저 1인당 하루 최대 몇 건까지 허용할지
- **방해금지 시간**: 기본 22:00~06:00 — 주요 유저 국가 기준으로 조정 (예: PH/MY)
- **승인 필요 여부**: 발송 전 결재를 받을지

### STEP 5. 성공 기준 정하기

무엇으로 성공을 판단할지 미리 정한다. 나중에 정하면 측정이 안 된다.

- 예: 발송 대비 메일 열람률 __% 이상, 발송군의 익일 재접속률이 대조군 대비 __%p 개선

---

## PHASE 2. 개발 요청 — 2건을 나눠서 요청

### 요청 A. 서버팀 (핵심, 공수 약 4 man-day)

> **요청 내용**: AE(운영 플랫폼)에서 오는 발송 요청을 받아 인게임 우편함으로 지급하는 엔드포인트를 만들어주세요.
>
> **첨부**: STEP 3의 필드 표 + 기술 명세 문서(webhook-server-example.md)
>
> **받아야 할 답**:
> 1. 엔드포인트 전체 주소 (예: `https://api.___/ae/engage/webhook`) — **이건 서버팀이 만들어야 생기는 값**
> 2. 완료 예정일

PM이 기술 스펙을 설명할 필요는 없다. 명세 문서를 첨부하고 위 2가지만 받으면 된다.

### 요청 B. 클라이언트팀 (효과 측정용, 공수 약 0.5 man-day)

> **요청 내용**: 유저가 우편함에서 메일을 열람할 때 이벤트를 하나 리포트해주세요 (`mail_opened`). 기존 트래킹 SDK를 그대로 쓰면 되고 신규 설치는 없습니다.

이게 없으면 "보냈다"까지만 알고 "봤다"를 알 수 없다. STEP 5의 성공 기준을 측정하려면 필요.

---

## PHASE 3. 플랫폼 설정 — 서버 개발과 병행 가능

PM 또는 운영 담당이 AE 콘솔에서 처리 (약 0.5 man-day):

1. Webhook 채널 생성 — URL(서버팀이 준 주소), 전송 ID(`#account_id`), 시크릿 Token 발급 후 서버팀에 안전하게 전달
2. 컨텐츠 템플릿에 STEP 3의 필드 입력
3. 도달 퍼널 ON, 테스트 허용목록에 QA 계정 등록
4. 피로도·방해금지 설정 (STEP 4에서 정한 값)

---

## PHASE 4. 검증 → 발송

1. **테스트 발송**: 허용목록 계정으로 test-send → 우편함 도착 확인
2. **중복 확인**: 같은 요청 재전송 시 보상이 두 번 지급되지 않는지 (QA 필수 항목)
3. **소규모 발송**: 전체가 아닌 일부(예: 5%)에 먼저 발송해 이상 없는지 확인
4. **본 발송** → 도달 퍼널(발송/도달/열람)과 STEP 5 지표 확인

---

## PM 체크리스트 (한 장)

**착수 전**
- [ ] 목적 한 문장 작성
- [ ] 채널이 Webhook이 맞는지 확인 (FCM/클라이언트로 되는 일 아닌지)
- [ ] 전달물 필드 표 확정
- [ ] 대상·빈도·시간대·승인 정책 확정
- [ ] 성공 기준 확정

**개발 요청**
- [ ] 서버팀: 명세 + 필드 표 전달 → 엔드포인트 주소·완료일 회신 받음
- [ ] 클라이언트팀: 열람 이벤트 요청

**설정·검증**
- [ ] 채널 생성 + 토큰 서버팀 전달
- [ ] 테스트 발송 성공 / 중복 지급 없음 확인
- [ ] 소규모 발송 후 본 발송

---

## 자주 하는 실수

| 실수 | 결과 |
|---|---|
| 필드 표 없이 "웹훅 붙여주세요"만 요청 | 개발 착수 불가, 왕복만 반복 |
| 목적 없이 채널부터 만듦 | Webhook이 필요 없는 일에 4 man-day 투입 |
| 중복 지급 테스트 생략 | 재시도 시 보상 이중 지급 사고 |
| 열람 이벤트 미구현 | 효과 측정 불가, 다음 캠페인 근거 없음 |
| 전체 발송부터 시작 | 문제 발견 시 이미 전 유저에게 나감 |
