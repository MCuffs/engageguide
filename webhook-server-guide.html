01동작 구조와 역할

누가 무엇을 담당하는가

Webhook 채널은 운영 플랫폼이 메시지를 직접 전달하지 않고, 발송해야 할 내용을 자사 서버로 넘기는 방식입니다. 실제 전달 수단은 서버가 정합니다 — 인게임 우편함, 사내 메시징, 외부 시스템 연동 등 무엇이든 가능합니다.

운영 플랫폼
대상 유저 선정 → 유저별로 발송 요청을 JSON으로 POST
→
수신 서버 (구현 대상)
서명 검증 · 중복 차단 · 자사 발송 로직 호출 · 결과 회신
→
유저
우편함 보상, 알림 등 실제 전달물 수령

요청은 유저 1명당 1건입니다. 대상 유저가 1만 명이면 1만 번의 POST가 발생하므로, 서버는 이 부하를 감당할 수 있어야 합니다.

다른 채널과의 차이 — 푸시 알림(FCM)이나 인앱 메시지(클라이언트 채널)는 서버 구현 없이 사용할 수 있습니다. Webhook은 자체 발송 로직이 필요할 때 선택하는 채널이며, 세 채널 중 개발 비용이 가장 큽니다.

02고정 규격과 자유 선택

반드시 이 값이어야 하는 것과, 직접 정하는 것

구현 전에 이 구분을 명확히 해야 합니다. 고정 표시 항목은 플랫폼이 정한 값이라 철자·대소문자까지 정확히 일치해야 하고, 자유 항목은 자사 컨벤션에 맞춰 정하면 됩니다.

시크릿 토큰 생성 — 아래 명령으로 만든 64자 hex 문자열을 채널 설정과 서버 환경변수에 동일하게 넣으면 됩니다. 메신저 평문 대신 비밀번호 관리자나 시크릿 저장소로 전달하세요.

openssl rand -hex 32

환경별 확인 필요 — 위 규격은 표준 문서 기준입니다. 서명 헤더의 이름, 서명 대상 범위, receipt 회신 주소는 사용 중인 환경의 채널 매뉴얼(채널 생성 화면 상단의 매뉴얼 링크)에서 확인해 맞추시기 바랍니다.

03컨텐츠 템플릿 = 개발 계약

채널 설정의 필드명이 곧 코드의 키가 된다

채널 생성 시 정의하는 컨텐츠 템플릿은 두 가지 역할을 동시에 합니다. 운영자가 메시지를 작성할 입력 폼이자, 서버가 받게 될 JSON의 구조입니다. 아래는 인게임 우편함 지급 시나리오의 예시입니다.

필드 (payload 키)표시 이름입력 방식필수예시값
title메일 제목텍스트필수복귀 보상이 도착했어요
body메일 본문텍스트필수7일 출석 보상을 확인하세요
reward_id보상 ID텍스트선택comeback_pack_01
expire_days만료일(일)텍스트선택7

필드 설계 요령

  • 운영자가 태스크마다 바꿔서 입력할 값만 필드로 만듭니다. 항상 고정인 값은 커스텀 파라미터로 처리하세요.
  • 보상 코드는 기존 기획 데이터의 코드 체계를 그대로 사용합니다. 웹훅용으로 새 체계를 만들면 매핑 테이블이 하나 더 생깁니다.
  • 숫자로 쓸 값이라도 payload에서는 문자열로 올 수 있습니다. 서버에서 파싱하고 기본값을 두세요.
  • 필드명은 나중에 바꾸기 어렵습니다. 확장 가능성(딥링크, 만료 정책 등)을 미리 고려하세요.

개인화 변수

운영자가 입력하는 값 안에 유저 속성을 삽입하면, 플랫폼이 수신자별로 실제 값으로 치환해서 전송합니다. 예를 들어 본문에 닉네임 속성을 넣으면 유저마다 다른 문구가 서버로 도착합니다. 서버는 이미 치환된 최종 문자열을 받으므로 별도 처리가 필요 없습니다.

자동 매핑이 아닙니다 — 플랫폼은 서버 내부 구조를 알지 못합니다. 템플릿에 reward_id라고 적으면 payload에 그 이름으로 실릴 뿐이고, 서버가 같은 이름으로 읽도록 구현되어 있어야 동작합니다. 양측이 이름을 약속하는 계약이며, 이 표가 그대로 개발 명세가 됩니다.

04DTO 정의

수신할 JSON의 형태 — C# / ASP.NET Core 기준

Models/WebhookPayload.cs
using System.Text.Json.Serialization;

public sealed class WebhookPayload
{
    // ↓ 이 5개 키 이름은 플랫폼 고정 규격이다 (02장 참조)
    [JsonPropertyName("message_id")] public string MessageId { get; init; } = "";
    [JsonPropertyName("user_id")]    public string UserId    { get; init; } = "";
    [JsonPropertyName("channel")]    public string Channel   { get; init; } = "";
    [JsonPropertyName("timestamp")]  public long   Timestamp { get; init; }
    [JsonPropertyName("content")]    public WebhookContent Content { get; init; } = new();
}

public sealed class WebhookContent
{
    // ↓ 컨텐츠 템플릿에 정의한 필드가 여기로 들어온다 (자유 명명)
    [JsonPropertyName("title")] public string Title { get; init; } = "";
    [JsonPropertyName("body")]  public string Body  { get; init; } = "";

    // ↓ 커스텀 필드와 커스텀 파라미터는 extra로 전달된다
    [JsonPropertyName("extra")] public Dictionary<string, string> Extra { get; init; } = new();

    // 미확인 필드를 흘리지 않고 받아두면 스키마 변경에 안전하다
    [JsonExtensionData] public Dictionary<string, object>? Unknown { get; init; }
}

착수 전 실제 payload를 확인하세요 — content 안에서 어떤 값이 최상위로 오고 어떤 값이 extra로 묶이는지는 환경에 따라 다를 수 있습니다. webhook.site 같은 임시 엔드포인트를 채널 URL에 넣고 시험 발송하면 실제 JSON과 서명 헤더 이름까지 그대로 확인할 수 있습니다. DTO는 그 결과로 확정하는 것이 재작업을 막는 가장 값싼 방법입니다.

05엔드포인트 구현

요청 수신부 — 검증하고, 큐에 넣고, 즉시 응답

Program.cs
app.MapPost("/engage/webhook", async (
    HttpContext http,
    WebhookService service,
    ILogger<Program> log) =>
{
    // (1) 원문 보관 — 서명 검증은 원문 기준이므로 역직렬화 전에 읽는다
    http.Request.EnableBuffering();
    using var reader = new StreamReader(http.Request.Body, leaveOpen: true);
    var raw = await reader.ReadToEndAsync();
    http.Request.Body.Position = 0;

    // (2) 서명 검증 — 헤더명은 채널 매뉴얼 규격에 맞출 것
    var signature = http.Request.Headers["X-Signature"].FirstOrDefault();
    if (!WebhookAuth.Verify(raw, signature))
    {
        log.LogWarning("서명 불일치 — 요청 거부");
        return Results.Unauthorized();
    }

    // (3) 파싱
    var payload = JsonSerializer.Deserialize<WebhookPayload>(raw);
    if (payload is null || string.IsNullOrEmpty(payload.MessageId))
        return Results.BadRequest(new { code = 400, msg = "invalid payload" });

    // (4) 큐에 적재하고 즉시 응답 — 성공 응답은 고정 규격
    await service.EnqueueAsync(payload);
    return Results.Ok(new { code = 0 });
});

왜 큐를 쓰는가

운영 태스크 한 건이 수천에서 수만 건의 호출을 만듭니다. 요청 스레드에서 DB 쓰기와 보상 지급까지 처리하면 응답이 지연되고, 플랫폼은 이를 발송 실패로 기록한 뒤 재시도합니다. 그 재시도가 다시 부하를 키우는 악순환이 생깁니다. 접수만 하고 즉시 200을 반환한 뒤 워커에서 처리하세요.

응답 코드 설계

상황응답플랫폼 동작
정상 접수200 + {"code":0}발송 성공으로 기록
서명 불일치401실패로 기록 — 재시도해도 동일하므로 설정을 고쳐야 함
payload 형식 오류400실패로 기록
서버 일시 장애500 또는 무응답재시도 대상 — 멱등성이 없으면 중복 처리 위험

06서명 검증

채널에 설정한 시크릿 토큰으로 요청의 진위를 확인

채널 생성 시 「채널 검증」을 켜면 시크릿 토큰을 등록하게 됩니다. 플랫폼은 이 토큰으로 요청에 서명을 붙여 보내고, 서버는 같은 토큰으로 재계산해 대조합니다. 토큰은 코드에 하드코딩하지 말고 시크릿 저장소에서 주입하세요.

Services/WebhookAuth.cs
public static class WebhookAuth
{
    private static readonly string Secret =
        Environment.GetEnvironmentVariable("WEBHOOK_SECRET")!;

    public static bool Verify(string rawBody, string? signatureHeader)
    {
        if (string.IsNullOrEmpty(signatureHeader)) return false;

        using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(Secret));
        var computed = Convert.ToHexString(
            hmac.ComputeHash(Encoding.UTF8.GetBytes(rawBody))).ToLowerInvariant();

        // 타이밍 공격 방지를 위한 고정시간 비교
        return CryptographicOperations.FixedTimeEquals(
            Encoding.UTF8.GetBytes(computed),
            Encoding.UTF8.GetBytes(signatureHeader.ToLowerInvariant()));
    }
}

규격 확인 필요 — 서명 헤더의 이름, 서명 대상(원문 전체인지 특정 필드 조합인지), 암호화 방식은 채널 설정 화면의 매뉴얼에 명시된 값을 따라야 합니다. 위 코드는 HMAC-SHA256 기준의 일반적인 형태입니다.

07처리 로직과 매핑

템플릿 필드를 자사 비즈니스 로직으로 연결하는 지점

Services/WebhookService.cs
public async Task ProcessAsync(WebhookPayload p)
{
    // (1) 멱등성 — 재시도로 인한 중복 지급 방지
    var key = $"webhook:{p.MessageId}";
    if (!await _cache.TrySetIfNotExistsAsync(key, "1", TimeSpan.FromDays(7)))
    {
        _log.LogInformation("중복 수신 무시: {Id}", p.MessageId);
        return;
    }

    try
    {
        // (2) 계정 조회 — user_id는 채널의 전송 ID로 지정한 속성값
        var account = await _mailbox.FindAccountAsync(p.UserId);
        if (account is null)
        {
            await _receipt.ReportAsync(p, success: false, error: "account_not_found");
            return;
        }

        // (3) ★ 템플릿 필드 → 서버 변수 매핑 지점 ★
        var title      = p.Content.Title;                                  // 필드: title
        var body       = p.Content.Body;                                   // 필드: body
        var rewardId   = p.Content.Extra.GetValueOrDefault("reward_id");   // 필드: reward_id
        var expireDays = int.TryParse(
            p.Content.Extra.GetValueOrDefault("expire_days"), out var d) ? d : 30;

        // (4) 자사 발송 로직 호출 — 기존 시스템을 그대로 재사용
        await _mailbox.SendAsync(new MailRequest
        {
            AccountId = account.Id,
            Title     = title,
            Body      = body,          // 개인화 변수는 플랫폼이 이미 치환해서 전달
            RewardId  = rewardId,
            ExpiresAt = DateTime.UtcNow.AddDays(expireDays),
            SourceTag = $"engage:{p.MessageId}",   // ★ 추적 키 — 09장에서 사용
        });

        // (5) 도달 이벤트 리포트 — 09장 참조
        await _analytics.TrackAsync(account.Id, "mail_delivered", new {
            message_id = p.MessageId, reward_id = rewardId
        });

        await _receipt.ReportAsync(p, success: true);
    }
    catch (Exception ex)
    {
        _log.LogError(ex, "처리 실패 {Id}", p.MessageId);
        await _cache.RemoveAsync(key);   // 재시도 허용을 위해 멱등키 해제
        await _receipt.ReportAsync(p, success: false, error: ex.Message);
    }
}

새로 만드는 것은 플랫폼의 JSON을 자사 도메인 객체로 번역하는 얇은 어댑터 한 층뿐입니다. 실제 발송은 이미 운영 중인 시스템(_mailbox.SendAsync)이 담당합니다.

SourceTag를 반드시 남기세요 — 우편함 레코드에 message_id를 저장해 두어야, 유저가 메일을 열었을 때 "어느 발송 건의 메일인지"를 클라이언트가 알 수 있습니다. 09장의 열람 이벤트가 이 값을 필요로 합니다.

08발송 결과 회신 (receipt)

receipt를 보내야 도달 퍼널이 정확해진다

Services/ReceiptReporter.cs
public async Task ReportAsync(WebhookPayload p, bool success, string? error = null)
{
    var payload = new
    {
        message_id = p.MessageId,                        // 받은 값 그대로
        user_id    = p.UserId,                           // 받은 값 그대로
        status     = success ? "success" : "failed",   // 이 두 문자열만 유효
        error_msg  = error ?? "",
        timestamp  = DateTimeOffset.UtcNow.ToUnixTimeSeconds(),
    };
    await _http.PostAsJsonAsync(_receiptUrl, payload);
}

계정을 찾지 못하거나 보상 코드가 유효하지 않은 등의 부분 실패를 성공으로 처리하면, 통계상으로는 모두 발송된 것처럼 보이지만 실제로는 전달되지 않은 유저가 생깁니다. 나중에 효과가 낮게 나와도 원인을 찾을 수 없습니다. 실패는 실패로 회신하고, error_msg에 사유를 남기세요.

09도달 퍼널 트래킹 코드

효과를 측정하려면 이벤트를 직접 올려야 한다

Webhook 채널은 플랫폼이 직접 전달하지 않기 때문에, "도달했는지 · 열어봤는지"를 플랫폼이 알 수 없습니다. 자사에서 트래킹 이벤트를 올려주어야 도달 퍼널이 채워집니다. 이 작업을 생략하면 "몇 건 보냈다"까지만 남고 효과 측정이 불가능합니다.

공통 규칙

  • 이벤트 속성에 message_id를 반드시 포함합니다. 이 값이 발송 건과 이벤트를 잇는 유일한 키입니다.
  • 이벤트명은 자유롭게 정하되, 채널의 「도달 퍼널 설정」에 등록한 이름과 정확히 일치해야 합니다.
  • 새로 만든 이벤트는 트래킹 플랜(이벤트 관리)에 등록해야 분석에서 정상 인식됩니다.
  • 이벤트를 올리는 주체가 로그인 상태(계정 식별 완료)여야 유저와 이벤트가 연결됩니다.

클라이언트 — 열람 이벤트

유저가 우편함에서 해당 메일을 열람하거나 보상을 수령할 때 리포트합니다. 07장에서 SourceTag로 저장해 둔 message_id를 메일 데이터와 함께 클라이언트로 내려주어야 합니다.

Unity (C#)

MailboxUI.cs
using ThinkingAnalytics;

public void OnMailOpened(MailData mail)
{
    // 서버가 내려준 message_id가 없으면(=운영 발송 메일이 아니면) 스킵
    if (string.IsNullOrEmpty(mail.MessageId)) return;

    var props = new Dictionary<string, object>
    {
        { "message_id", mail.MessageId },   // ★ 퍼널 연결 키 — 필수
        { "channel",    "webhook" },
        { "mail_id",    mail.Id },
        { "action",     "open" }           // open / claim 구분이 필요하면
    };

    TDAnalytics.Track("mail_opened", props);
}

채널 설정과 연결

이벤트를 올리는 것만으로는 퍼널이 채워지지 않습니다. 채널의 「도달 퍼널 설정」을 켜고, 위에서 정한 이벤트명을 각 단계에 등록해야 합니다.

퍼널 단계등록할 이벤트명리포트 주체시점
발송— (플랫폼 자동)플랫폼webhook 호출 시
도달mail_delivered서버우편함 메일 생성 직후
클릭 · 열람mail_opened클라이언트유저가 메일 열람 / 보상 수령 시

흔한 실수 세 가지

① message_id를 속성에 넣지 않음 — 이벤트는 쌓이지만 발송 건과 연결되지 않아 퍼널이 비어 있습니다.

② 채널 설정의 이벤트명과 코드의 이벤트명 불일치 — 오탈자 하나로 퍼널이 0건이 됩니다.

③ 트래킹 플랜에 이벤트 미등록 — 데이터는 들어오지만 분석 화면에서 선택할 수 없습니다.

발송 트래픽이 크고 기존 API에 영향을 주고 싶지 않다면, 전용 Deployment로 분리하고 HPA를 설정하는 구성을 권장합니다. 발송은 짧은 시간에 집중되는 스파이크성 부하이므로, 최소 레플리카보다 스케일 아웃 속도가 중요합니다.

11검증 절차

배포 → 채널 연결 → 실제 발송 순으로 단계별 확인

1단계 · 서버 단독 검증

verify.sh
BODY='{"message_id":"test_1","user_id":"TEST_ACCOUNT","channel":"webhook",
"timestamp":0,"content":{"title":"테스트","body":"본문",
"extra":{"reward_id":"comeback_pack_01","expire_days":"7"}}}'

SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$WEBHOOK_SECRET" | awk '{print $2}')

curl -X POST https://<도메인>/engage/webhook \
  -H "Content-Type: application/json" \
  -H "X-Signature: $SIG" \
  -d "$BODY"
  • 정상 응답 반환 ({"code":0})
  • 테스트 계정 우편함에 전달물 도착 (보상 첨부 포함)
  • 동일 요청 재전송 시 중복 지급되지 않음 — 가장 중요한 항목
  • 서명을 틀리게 보내면 401 반환

2단계 · 채널 연결 검증

  • 채널 생성 후 테스트 허용목록에 QA 계정 등록
  • 채널 테스트 발송으로 실제 전달 확인
  • receipt가 플랫폼에 기록되는지 확인

3단계 · 트래킹 검증

  • mail_delivered 이벤트가 유입되고 message_id 속성이 채워져 있음
  • QA 계정으로 메일 열람 후 mail_opened 이벤트 유입 확인
  • 도달 퍼널에서 발송 → 도달 → 열람이 단계별로 집계됨

4단계 · 소규모 발송

전체 대상이 아닌 일부(예: 5%)에 먼저 발송해 실패율과 지연을 확인한 뒤 본 발송을 진행하세요. 문제가 있어도 영향 범위를 제한할 수 있습니다.

12체크리스트

구현 전 확정 사항과 완료 기준

착수 전 확정

  • 엔드포인트 도메인 · 경로 결정 (자사 API 컨벤션에 맞춰)
  • 컨텐츠 템플릿 필드 표 확정 — 서버 DTO와 동일한 이름
  • 전송 ID로 사용할 유저 속성 결정 — 서버가 계정 조회 가능한 키
  • 시크릿 토큰 생성 및 안전한 경로로 서버팀 전달
  • 서명 헤더명 · 서명 대상 · receipt 회신 주소를 매뉴얼에서 확인
  • 도달 · 열람 이벤트명 결정

서버 구현 완료 기준

  • POST 수신 · 서명 검증 · 파싱 · 큐 적재 · 즉시 200 응답
  • message_id 기준 멱등성 보장
  • 자사 발송 로직 연동 + message_id를 레코드에 저장
  • 성공 · 실패 receipt 회신
  • 도달 이벤트 리포트

클라이언트 구현 완료 기준

  • 메일 데이터에 message_id 전달 경로 확보
  • 열람 · 수령 시 이벤트 리포트 (message_id 속성 포함)

플랫폼 설정 완료 기준

  • 채널 생성 (URL · 전송 ID · 시크릿 토큰 · 컨텐츠 템플릿)
  • 도달 퍼널 설정 ON + 이벤트명 등록
  • 트래킹 플랜에 신규 이벤트 2종 등록
  • 테스트 허용목록 · 발송 빈도 · 방해금지 설정

필드나 이벤트를 추가할 때

예를 들어 이동 링크(deep_link)를 추가한다면 양쪽을 함께 변경해야 합니다. 채널의 컨텐츠 템플릿에 행을 추가하고, 서버에서 Extra.GetValueOrDefault("deep_link")를 읽도록 구현합니다. 이벤트도 마찬가지로 코드의 이벤트명과 채널 설정, 트래킹 플랜 세 곳이 모두 일치해야 합니다. 한쪽만 바꾸면 값이 조용히 무시됩니다 — 자동 매핑이 아니라 이름 약속이기 때문입니다.

Webhook 채널 수신 서버 구현 가이드 · 코드는 C# / ASP.NET Core 및 각 플랫폼 SDK 기준 참조 구현입니다. 서명 규격, 응답 형식, receipt 회신 주소는 사용 중인 환경의 채널 매뉴얼을 확인해 맞추시기 바랍니다.
